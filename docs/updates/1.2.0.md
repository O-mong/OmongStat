# OmongStat 1.2.0 update

This update hardens anonymous collection, database maintenance, statistics queries, and plugin packaging. It also documents the local sample API and automatic React build used by the deployment workflow.

The WordPress plugin version is **1.2.0** and the database schema version is **2**. The development package's `package.json` version is separate from the WordPress release version. The security changes do not redesign the React dashboard or change its chart selector.

For first-time installation, use the [installation guide](../../README.md#installation). For imports and routine operations, see [Development and operations](../DEVELOPMENT.md).

## Changes at a glance

| Area | Previous behavior or exposure | Updated behavior |
| --- | --- | --- |
| Public collection | Anonymous requests could produce unlimited event writes at the application layer | Shared, atomic site and IP minute budgets; 429 on excess and 503 if limit storage fails |
| Origin handling | No explicit collection origin restriction | Reject explicit foreign or opaque origins; accept configured site origins and missing Origin |
| Referrers | URL credentials, queries, and fragments could persist | Strip these components on collection, import, statistics reads, and background cleanup |
| Failure logging | Database errors could include SQL or request details | Plugin failure messages use an operation name and keyed fingerprint |
| Migration work | Public requests could perform upgrade work; backfill was not resumable | Activation, administrator, or cron upgrade; resumable batches and failure backoff |
| Event lifetime | No configurable automatic retention | Keep all by default; administrators can explicitly enable age-based deletion |
| Statistics | Repeated aggregate queries had no application query budget/cache | Ten-second server cache and database execution-time controls |
| Runtime assets | Manifest paths and filesystem entries needed stronger validation | Explicit file list, safe manifest paths, and symlink/special-file rejection |
| Docker backup | Previous plugin copies could remain under the public plugins directory | Private backup directory outside the web root, including relocation of old backups |
| Docker file permissions | Runtime files could be directly writable by the web process | Root-owned deployment files readable by the web-server group |
| Local development | Development server exposure needed tighter defaults | Loopback binding, disabled CORS, restricted hosts; mock API remains development-only |

## 1. Public collection and API behavior

Implementation: [security.php](../../wordpress_plugins/omongstat/includes/security.php), [collect.php](../../wordpress_plugins/omongstat/includes/collect.php).

`POST /wp-json/omongstat/v1/collect` remains public so logged-out visits can be recorded. It does not require a WordPress REST nonce. Existing payload type, length, internal-path, and 16 KiB body checks remain in place.

The new limiter uses the site's `<prefix>omongstat_limits` table rather than process-local counters. Atomic counter increments let multiple PHP workers share a budget. It evaluates the site bucket before the IP bucket, and stores HMAC bucket keys rather than raw IP addresses. Expired buckets are removed incrementally during collection and maintenance.

| Policy | Default |
| --- | --- |
| Site budget | 3,000 requests per minute |
| IP budget | 120 requests per minute |
| Window | Fixed 60-second epoch window |
| Excess requests | HTTP 429 with seconds until the next window in `Retry-After` |
| Counter storage failure | HTTP 503; no event inserted |

Rejected or invalid requests that reach the limiter can consume a budget. Concurrent requests can be rejected conservatively near the limit. Fixed windows allow bursts across a minute boundary. Requests still reach PHP and the database: these controls do not replace reverse-proxy or CDN traffic limits.

Allowed origins default to WordPress `home_url()` and `site_url()`, comparing scheme, host, and effective port. An explicit foreign origin or opaque `null` origin returns 403. Requests without Origin remain supported. Origin checking is a browser-facing restriction, not visitor authentication; anonymous events can still be fabricated by non-browser clients.

| Collection response | Meaning |
| --- | --- |
| 204 | Event stored successfully; empty response body |
| 400 | Invalid JSON or payload values |
| 403 | Explicit Origin is not allowed |
| 413 | Body exceeds the size limit |
| 429 | Collection budget exceeded |
| 500 | Event database operation failed |
| 503 | Rate-limit storage is unavailable |

Responses retain `Cache-Control: no-store, private, max-age=0`. A successful `sendBeacon()` return only means the browser accepted the transmission for delivery; it does not confirm a 204 or database insert.

### Optional server-side configuration

Use a server-managed MU plugin for overrides. The following example keeps the shipped budgets and allows an additional example origin; replace or omit the origin as appropriate:

```php
add_filter('omongstat_rate_limits', function () {
    return ['site' => 3000, 'ip' => 120];
});

add_filter('omongstat_allowed_origins', function ($origins) {
    $origins[] = 'https://example.org';
    return $origins;
});
```

Each budget is clamped to 1–100,000. Configure both keys when overriding the limits. Behind HTTPS termination, ensure WordPress resolves its public URLs with the correct HTTPS scheme.

Forwarded client IP and country headers remain untrusted by default. Only configure `omongstat_trusted_proxies` for directly connected proxies that remove or overwrite client-supplied forwarding headers. Without that configuration, visitors behind a reverse proxy share its IP budget. The [proxy setup guide](../DEVELOPMENT.md#신뢰할-프록시-설정) explains the existing identity rules.

## 2. Stored data and failure logs

Implementation: [security.php](../../wordpress_plugins/omongstat/includes/security.php), [import.php](../../wordpress_plugins/omongstat/includes/import.php), [migration.php](../../wordpress_plugins/omongstat/includes/migration.php).

Referrers now retain only HTTP(S) scheme, host, optional port, and path. For example, `https://example.org/article?campaign=sample#section` becomes `https://example.org/article`. Embedded URL credentials are also removed. Invalid referrers are reduced to an empty value.

The same sanitizer applies to new browser events and imported logs. Existing rows are scrubbed in background batches. Statistics responses sanitize old values immediately, even before the stored-data cleanup finishes. During that transition, referrer rankings may differ from fully cleaned database aggregates because old groups are sanitized and combined after the initial top-50 selection.

Scrubbing permanently removes these URL components. It does not remove whole event rows, identify secrets inside paths, or rewrite old backups and access logs. Existing raw user-agent storage and pseudonymous visitor/session IDs remain; this release does not claim that analytics data is anonymous.

Plugin-generated failure messages contain an operation and a short keyed fingerprint, allowing repeated failures to be correlated without copying raw SQL or payloads into the plugin log message. This does not govern logging by WordPress core, other plugins, the database server, or the proxy. Keep production `WP_DEBUG_DISPLAY` disabled.

## 3. Schema upgrade, background work, and retention

Implementation: [migration.php](../../wordpress_plugins/omongstat/includes/migration.php), [maintenance.php](../../wordpress_plugins/omongstat/includes/maintenance.php), [admin.php](../../wordpress_plugins/omongstat/includes/admin.php), [uninstall.php](../../wordpress_plugins/omongstat/uninstall.php).

Schema version 2 adds the shared rate-limit table and initializes maintenance state. The schema version advances only after a successful migration. Existing legacy `occured_at` migration and conflicting-timestamp preservation remain in place; old invalid paths and missing historical visitor/session IDs are not invented or reconstructed.

- Activation can run the upgrade directly. Authorized administrator requests and a scheduled upgrade job also run it. Public page initialization schedules work instead of performing the schema migration inline.
- Migration lock acquisition does not wait for another worker. Failed upgrades set a five-minute retry cooldown. Database DDL can still take time when an upgrade actually runs.
- Background work scans at most 250 events per run using a persisted ID cursor. It cleans referrers and classifies previously unknown user agents. Completed batches survive retries.
- Maintenance removes expired limit buckets in batches of 500. It schedules another run after approximately a minute while work remains, otherwise after an hour. These are scheduling targets, not guaranteed execution times.
- WordPress cron must run. If `DISABLE_WP_CRON` is enabled, invoke WordPress cron from the site's scheduler. Collection can return 503 before the new limit table is available.

The new **Event retention in days** setting defaults to **0: keep all events**. A positive value, up to 3,650 days, enables permanent deletion of events older than the elapsed UTC age cutoff, in batches of at most 500. This differs from the site-timezone calendar boundaries used by dashboard date selection.

Deactivation preserves data. Uninstall clears scheduled plugin jobs, but retains stored data unless the existing explicit deletion option is enabled. With that option enabled, uninstall removes both event and rate-limit tables and plugin settings/state.

## 4. Administrator statistics

Implementation: [rest-stats.php](../../wordpress_plugins/omongstat/includes/rest-stats.php).

The seven existing routes and response shapes are preserved. They still require the `manage_options` capability and a valid WordPress REST nonce. The security work does not modify React components or add mock-related UI controls.

Successful results are cached in WordPress transients for ten seconds, keyed by version, event table, endpoint, and date range. This is a server-side result cache; HTTP responses still prohibit caching. Refresh can therefore show data up to ten seconds old.

MariaDB queries use a three-second `max_statement_time` budget. MySQL receives a `MAX_EXECUTION_TIME(3000)` optimizer hint; enforcement depends on the database's support. These are query controls, not a three-second deadline for the entire HTTP request. Database failures remain HTTP errors rather than empty charts.

## 5. Build, ZIP, and Docker deployment

Implementation: [package.mjs](../../scripts/package.mjs), [validate-package.mjs](../../scripts/validate-package.mjs), [archive.py](../../scripts/archive.py), [deploy-plugin.sh](../../wordpress_plugins/omongstat/deploy-plugin.sh).

Docker deployment automatically runs `npm run build` to compile TypeScript and generate the Vite static files. The legacy `--build` flag remains accepted but is no longer necessary. A failed build exits before upload and preserves its failure status. Required files and the manifest are validated before the staged plugin replaces the existing installation.

The shared package validator accepts the explicit PHP/collector runtime files and manifest-listed JS/CSS assets. It rejects escaping paths, symlinks, special files, and unexpected entries under runtime directories. PHP also validates manifest asset paths before enqueueing them. ZIP creation checks symlinks independently and writes through a temporary archive before replacing the final ZIP.

The installation ZIP has one top-level `omongstat/` directory. React source, mock data, dependencies, environment files, documentation, and deployment scripts are excluded. Python is used for archive creation and some tests; it is not a production API or storage service.

The Docker script retains staging, validation, deployment locking, and restoration of the previous plugin when replacement fails. Its shipped defaults are:

| Item | Default |
| --- | --- |
| Container | `wordpress-web`, overridable with `WORDPRESS_CONTAINER` |
| Installation directory | `/var/www/html/wp-content/plugins/omongstat` |
| Backup directory | `/var/backups/omongstat`, outside the web root |
| Backup parent permissions | 700 |
| Installed ownership | `root:www-data` |
| Installed directory/file modes | 750 / 640 |

Legacy `.omongstat.stage.*.previous` backup directories are relocated outside the public plugins directory during deployment. Backups are not automatically rotated or deleted. Mount the backup location persistently if it must survive container replacement.

The web process cannot directly edit root-owned plugin files. Use the deployment script for subsequent Docker updates. A writable parent plugins directory can still allow its owner to replace the whole directory; full filesystem isolation requires infrastructure controls such as a read-only mount. Normal WordPress ZIP installations retain the platform's usual ownership behavior.

## 6. Local sample API and exposure

Implementation: [mockApi.ts](../../dev/mockApi.ts), [sampleData.ts](../../dev/sampleData.ts), [vite.config.ts](../../vite.config.ts).

`npm run dev` attaches a read-only mock API to Vite using the same statistics paths as WordPress. It generates 90 days of in-memory sample events, injects the development WordPress configuration and mount ID, and leaves the existing React fetch layer intact. There is no SQLite database, persistence, or separate Python API.

Use `OMONGSTAT_MOCK_SCENARIO=empty`, `error`, or `slow` with `npm run dev` to exercise response states, or the `mock` query parameter for an individual request. The middleware is enabled only for development and is excluded from the production plugin.

Vite defaults to loopback, CORS disabled, and restricted host handling. The development port is strict, so a conflict fails instead of silently choosing another port. Preview also binds to loopback. Publishing the WordPress plugin does not require leaving Vite running.

## 7. Upgrade and recovery

1. Back up the WordPress database and current plugin files. The Docker script's automatic backup contains plugin files only.
2. Install the built ZIP or run the Docker deployment script. Build/validation failures should leave the current installation intact.
3. Open the WordPress administration area and ensure scheduled jobs can run. Check for migration errors before testing collection.
4. Confirm public WordPress URLs and trusted-proxy settings. Keep retention at 0 unless historical deletion is intended.
5. Clear page and optimized JavaScript caches. Bypass CDN/proxy caching for both `/wp-json/` and `?rest_route=` requests.
6. Make a logged-out visit, confirm collection returns 204, and verify the event in Analytics after the short statistics cache expires.

File replacement rollback does not undo database changes, background referrer scrubbing, or retention deletion. Restoring an older code backup is not a schema downgrade. Recover removed data from an appropriate database backup; restoring it may discard newer events, so plan that recovery separately.

The [Nginx configuration example](../../config/nginx-omongstat.conf.example) is a template, not an applied infrastructure change. Adapt it to the existing proxy, run `nginx -t`, and deploy through the site's normal infrastructure process. Configure equivalent CDN limits and cache bypass for both REST URL forms. Avoid changing unrelated upload limits.

## 9. Public repository hygiene

Examples use placeholder domains and documented script defaults. Do not commit actual access logs, database exports, credentials, private keys, customer data, or server-specific configuration. Keep local proxy settings under `config/local/`, private notes under `docs/private/`, and database exports/backups under `backups/`; publish sanitized `.example` templates separately.

The ignore rules cover those local directories, compressed database dumps, rotated logs, common certificate/key containers, existing environment files, dependencies, and generated bundles. Existing deployment-script ignore rules are preserved. This is a convenience against accidental additions, not a secret scanner or access-control boundary. Plain SQL exports belong in the ignored backup directory; SQL source files elsewhere are not blanket-ignored.

**Ignore rules do not untrack files or erase Git history.** At the time of this update, the deployment script and some generated admin assets are already tracked, despite matching ignore rules. Review them as public source until they are deliberately removed from the index. No Git history or tracked-file removal is performed by this documentation update. If a real credential has already been published, revoke or rotate it; adding an ignore rule is insufficient.
